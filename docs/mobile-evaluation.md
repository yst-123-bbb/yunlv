# 移动端选型评估（云旅AI v2）

> 依据：`design.md` 契约 C-API@1（HTTP 接口）。
> 结论摘要：本期移动端**只做选型评估，不实现 App 代码**；后端能力已由 C-API@1 完整覆盖，移动端只需复用 HTTP 接口。首选 **uni-app（微信小程序 + H5 双端）**，Flutter 作为后续需要更高交互动效或独立 App 品牌时的备选。

---

## 1. 复用的 API 端点清单

移动端全部通过 C-API@1 的 JSON 接口读写数据，不新增后端专用接口。基础地址默认 `http://127.0.0.1:8000`（`APP_BASE_URL` 可覆盖）。

| 方法 | 路径 | 请求参数 | 响应键 | 移动端用途 |
|---|---|---|---|---|
| POST | `/api/plan` | body `{"user_data": {...}}` | `session_id`、`stage`、`state` | 创建会话（表单提交） |
| POST | `/api/plan/{session_id}/stage/{stage}` | body `{"payload": {...}}` | `state` | 分步填写与推进阶段 |
| POST | `/api/plan/{session_id}/back` | - | `state` | 返回上一步 |
| GET | `/api/plan/{session_id}` | - | `state` | 行程页拉取与断网后刷新 |
| POST | `/api/plan/{session_id}/modify` | body 为 `patch`（`remove`/`replace`/`reorder`） | `state`、`issues` | 行程拖拽/删除/替换 |
| GET | `/api/transport?origin=&dest=&date=` | query | `offers`、`attempted` | 交通方案列表 |
| GET | `/api/tickets?place=&city=` | query | `offers`、`attempted` | 门票与预约信息 |
| POST | `/api/notes` | body `{"url": str}` | `NoteItem` | 粘贴小红书链接导入攻略 |
| GET | `/api/budget?session_id=` | query | `BudgetBreakdown` | 预算分项与分档展示 |
| GET | `/api/places?city=&keyword=&limit=` | query | `items`、`attempted` | 景点/美食/酒店搜索 |
| GET | `/api/route?from_lng=&from_lat=&to_lng=&to_lat=&mode=` | query | `distance_m`、`duration_s`、`polyline` | 地图时间轴与耗时计算 |
| POST | `/api/share` | body `{"session_id": str}` | `short_id`、`url` | 生成分享链接 |
| GET | `/api/share/{short_id}` | - | `plan`（只读 PlanSession） | 小程序分享落地页 |
| GET | `/api/plan/{session_id}/export.ics` | - | `text/calendar` | 导入手机日历 |
| GET | `/api/plan/{session_id}/export.pdf` | - | `application/pdf` | 行程单下载 |
| GET | `/api/plan/{session_id}/export.png` | - | `image/png` | 长图保存到相册 |

约定与失败语义（直接影响移动端交互设计）：

- 会话不存在 → `404 {"detail":"session_not_found"}`：移动端回到表单页并提示重新创建。
- 参数校验失败 → `422`：表单侧先行校验，避免依赖服务端报错。
- 未捕获异常 → `500 {"detail":"internal_error"}`：统一展示「服务繁忙，请稍后重试」，不做错误细节透出。
- `POST /api/share` 以 `session_id` 幂等，重复点击分享不会产生多条分享记录。
- 导出接口返回二进制流，小程序需走 `wx.downloadFile` / `uni.downloadFile`，Flutter 需走 `dio.download`，与 JSON 请求分离。

选型对接口的依赖结论：C-API@1 的 17 个端点已覆盖「创建 → 分步 → 行程编辑 → 交通/门票/攻略 → 预算 → 地图 → 分享 → 导出」全部移动端场景，**无需为小程序或 Flutter 单独设计接口**。

## 2. uni-app 与 Flutter 对比结论

| 维度 | uni-app | Flutter |
|---|---|---|
| 开发成本 | **低**：一份 Vue 代码编译到微信小程序 + H5，与现有 `web/`（Vue/React 组件与 CSS 变量体系）思路接近，复用现有 API 客户端与页面结构，人力约 2–3 人周完成 MVP；拖拽排序、长图保存等直接用平台能力 | **中高**：需独立维护 Dart 代码库，所有页面重写，状态管理（Riverpod/Bloc）与地图组件需额外选型，人力约 5–7 人周；与 Web 端无法共享任何代码 |
| 包体积 | **小**：微信小程序主包 2MB 上限、总包 20MB；本项目页面少（表单、行程、预算、地图、分享），主包可控在 1.5MB 内；H5 产物复用现有 Vite 构建 | **大**：Android APK 约 15–25MB、iOS IPA 约 30–50MB（含 Skia 引擎），需按 ABI 拆分；小程序场景无法直接上架，必须另做原生 App 或转 H5 |
| 审核周期 | **短**：微信小程序首次审核 1–3 个工作日，类目为「旅游-信息服务」；需提供隐私政策与用户信息收集说明；迭代审核通常 1 个工作日内 | **长**：Google Play 首次审核 1–7 天，App Store 首次审核 1–3 天且合规问询概率高（UGC 内容需说明审核机制）；国内 Android 应用商店（华为/小米/OPPO/vivo）各需单独提交，合计 1–2 周 |

**结论**：本期及近期发布走 **uni-app / 微信小程序**——开发成本最低、可直接复用 C-API@1 与分享落地页（`/api/share/{short_id}`），审核周期可控。Flutter 仅在出现以下需求时再评估：需要小程序无法承载的复杂动画/离线地图、需要独立品牌 App 上架、或需要深度调用设备传感器。两者均不修改后端接口。

## 3. 隐私政策与权限最小化清单

### 3.1 收集的信息

| 数据项 | 是否必需 | 用途 | 存储位置 |
|---|---|---|---|
| 目的地城市、出行日期、人数、预算 | 必需 | 生成行程与预算 | 服务端会话文件（`{cache_dir}/sessions/{session_id}.json`） |
| 人群模式（亲子/老人/无障碍） | 可选 | 调整每日强度与提示 | 同上 |
| 用户粘贴的小红书链接 | 可选 | 单链导入攻略摘要 | 服务端缓存，不落库为个人信息 |
| 偏好选择/跳过记录 | 可选 | 本地加权排序 | 服务端 `{cache_dir}/preferences.json` |

**不收集**：精确 GPS 定位（地图坐标由城市/景点名解析）、通讯录、相册（仅保存长图时写入）、手机号与实名信息。

### 3.2 权限最小化清单

| 权限 | 申请时机 | 必要性 | 说明 |
|---|---|---|---|
| 网络访问 | 建立会话时 | 必需 | 调用 C-API@1 |
| 相册写入（保存行程长图） | 用户点击「保存长图」时 | 按需 | 仅在导出 PNG 后申请，拒绝时降级为复制链接 |
| 日历写入（导入行程） | 用户点击「加入日历」时 | 按需 | 仅在下载 ICS 后申请，拒绝时降级为下载文件 |
| 剪切板读取（粘贴小红书链接） | 用户主动点击「粘贴」 | 按需 | 不后台读取 |
| 位置信息 | 不申请 | 不需要 | 不使用 GPS |
| 相机/麦克风/通讯录 | 不申请 | 不需要 | 无相关功能 |

### 3.3 隐私政策要点（需在小程序后台与实际页面同时展示）

1. 明确说明信息仅用于生成行程与预算，**不向第三方出售**；第三方数据来源（高德地图、小红书、景区官网）以链接与来源标注形式披露。
2. 说明分享页 `/share/{short_id}` 为**只读公开链接**，用户分享即视为同意他人可查看该行程内容，链接不含账号信息。
3. 提供删除路径：会话与偏好记录按期清理，用户可申请删除会话数据。
4. 未成年人：人群模式含「亲子」不等于面向儿童，不采集儿童个人信息。
5. 留存期限：会话与偏好文件按本地缓存 TTL 清理，超期自动删除。

## 4. 鸿蒙与平板的流量评估结论

### 4.1 鸿蒙（HarmonyOS）

- **技术可行性**：uni-app 已提供 HarmonyOS Next 编译目标；Flutter 对鸿蒙支持依赖社区 SDK，成熟度偏低。故鸿蒙端同样倾向 uni-app 方案。
- **流量评估**：鸿蒙用户占国内存量约 15%–20% 且集中在中高端机型，与「预算敏感型出行规划」用户重叠度中等。**短期结论：不单独为鸿蒙出包**，先以 H5（uni-app 编译产物）覆盖鸿蒙浏览器与元服务内置 WebView；待微信小程序端月活稳定后，再评估用同一套 uni-app 代码编译鸿蒙元服务包，预计增量成本 3–5 人日（主要是签名与上架流程）。
- **上架成本提示**：鸿蒙元服务需完成华为云备案（ICP 备案）后方可正式发布，周期以周计，需提前准备材料。

### 4.2 平板

- **技术可行性**：小程序在平板端以放大的手机布局运行，现有 `web/` 的 <768px 响应式规则与 CSS 变量体系可直接复用；Flutter 需额外编写自适应断点布局。
- **流量评估**：平板用户占比低（移动端整体 <5%），且使用场景偏「出行前大屏查看行程」，与分享页、PDF 行程单高度契合。**结论：不为平板单独适配**，仅保证分享页 `SharePage` 与行程页在大屏下不出现拉伸变形（最大宽度约束 + 居中布局），引导平板用户使用分享链接或 PDF 导出。

### 4.3 综合结论

- 首发：微信小程序（uni-app）+ 现有 Web + 分享页，覆盖手机与平板浏览器。
- 不投入：原生 App（Flutter）、鸿蒙独立包、平板专用布局。
- 触发条件再评估：小程序月活 > 1 万或出现鸿蒙渠道明确投放需求时，启动 uni-app 鸿蒙包；出现复杂动画/离线地图需求时，启动 Flutter 评估。
